# e2e-harness — live full-TUI evaluation harness (rebuilt 2026-09-13)

Rebuilt 2026-09-13 after the earlier harness was lost. This is the mandatory
gate for all product claims: no task is done without live full-TUI evidence
from this harness against current host versions.

## Security contract

The harness stores, reads, and prints **zero credentials**. The provider key is
resolved by `provider-key.sh`, in this order:

1. the caller's environment (`export OPENROUTER_API_KEY=...` wins, so a campaign
   can be run against a chosen key);
2. the local OpenCode credential store
   (`${XDG_DATA_HOME:-~/.local/share}/opencode/auth.json`, the `openrouter`
   entry) — which is where the host itself keeps provider keys and where a
   developer on this machine already has one, so a campaign runs from a fresh
   shell without the caller having to know where the key lives.

Either way the key reaches the tmux session environment, and on the v1 host
also the gitignored isolated credential store the launcher writes (the stock
v1 host resolves the key from `auth.json` at boot and never renders command
replies without one). No tracked file contains a secret;
`cfg/opencode.json` and `cfg-v1/opencode.json` declare the
provider through `env: ["OPENROUTER_API_KEY"]` with no `apiKey` field. The
resolver prints no key material — a missing key is reported by naming the two
places it was looked for. Confirm with:

    rg -iN 'sk-or-v1-[A-Za-z0-9_-]{8,}' hack/e2e-harness/   # expect no matches

## Layout

- `launch.sh`    — v2: opencode2 --standalone, tmux session `fixate-on`, cfg/ (server plugin + cli.json v2 companion)
- `launch-v1.sh` — v1: stock brew opencode, isolated HOME, tmux session `fixate-on`, cfg-v1/ (server plugin + tui.json v1 companion)
- `drive.sh`     — v2 palette-driven campaign: Add Goal -> poll state.json -> Dashboard -> live-update detection -> Escape close
- `drive-f2.sh`  — v1 toast-discipline laws: L1 zero JSON toasts, L2 curated moment, L3 no screen-covering
- `drive-cockpit-v1.sh` — v1 cockpit C1–C6 via the command palette: dashboard opens, goal list renders, detail card, action menu, back to list, close. Asserts dialog-only markers and asserts their ABSENCE to confirm close.
- `cfg/`         — v2 server config (openrouter/nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free, goal-command template, Implementer agent) + cli.json (v2 TUI companion) + agents/
- `cfg-v1/`      — v1 server config + agents/ (tui.json is generated into the isolated HOME by launch-v1.sh)
- `work/`        — v2 build fixture: deliberately BROKEN src/math.js (add returns a-b, no multiply) + failing tests + SPEC.md
- `work-v1/`     — v1 build fixture (same broken state)
- `captures/`    — ANSI captures + state.json snapshots + freeze PNGs written by the drive scripts
- `captures/freeze/` — PNG renders of key ANSI captures via [charmbracelet/freeze](https://github.com/charmbracelet/freeze) (v0.2.2, installed as `freeze`). Generated by drive.sh and drive-f2.sh at campaign end. Freeze absence degrades gracefully (warn, never fails the campaign) — the ANSI body-diff remains the authoritative live-update gate.

## Self-modification is a failure, not a result

The campaign's agent runs INSIDE the host this harness scores. It has been
observed editing the harness's own `verifierCommand` (`verifier-working.sh`) while
a campaign was asserting on the product — twice, once on 2026-10-01 and once in
`c0a62dd`. (That option was pruned on 2026-11-01: the plugin no longer runs any
program to check a claim, so `cfg/opencode.json` no longer configures one and
`verifier-working.sh` is kept only as the historical record of the incident.)
An instrument the subject can rewrite cannot testify about the subject,
so every driver now calls `assert_harness_unmodified` before it touches the host,
and fails loudly naming the file when the harness tree differs from HEAD. Restore
it with `git checkout -- hack/e2e-harness`, or commit the change deliberately
and re-read it as a review finding rather than as campaign evidence.

`captures/`, `work/` and `work-v1/` are excluded from that check: they are
generated, and the campaign is supposed to change them.

## Usage

    bash hack/e2e-harness/launch.sh        # v2 full TUI in tmux
    bash hack/e2e-harness/drive.sh         # palette-driven campaign (requires launch.sh running)
    bash hack/e2e-harness/launch-v1.sh     # v1 full TUI in tmux (isolated HOME)
    bash hack/e2e-harness/drive-f2.sh      # v1 toast-law campaign (requires launch-v1.sh running)
    tmux attach -t fixate-on                  # watch (do NOT kill sessions you don't own)

## Session law (one session, fixate-on)

The campaign interacts with exactly one tmux session, `fixate-on`, and nothing
in this repository creates, kills, or addresses a session under any other
name. Both hosts live in it sequentially — run-all's leases already serialize
v1 and v2 — and the extra hosts a campaign needs (the multi-session scenarios)
run as WINDOWS inside it, killed as windows at scenario end. The launchers
kill only the one session they are about to create.

Each v1 campaign opens a FRESH HOST SESSION (<leader>n, the host's own
new-session chord) after its boot settle and before its first goal command,
gated on the home route's own marker. Measured 2026-10-24: all six campaigns
shared one host session, and the model's agent-channel goal-command duplicates
can land minutes after the template that requested them — one destroyed the
next campaign's 25-second-old goal. A stale in-flight tool call is bound to
the session whose context holds it, so per-campaign host sessions make every
late or replayed dispatch land in the campaign that issued it.

## Freeze visual evidence (charmbracelet/freeze)

Both drive scripts render key ANSI captures to PNG under `captures/freeze/`
using the `freeze` command (https://github.com/charmbracelet/freeze, v0.2.2).

- **v2 (drive.sh)**: renders boot, after-add, dashboard-open, last-live-poll, and
  closed captures as `v2-*.png`.
- **v1 (drive-f2.sh)**: renders boot, after-create, after-churn, and after-clear
  captures as `v1-*.png`.

The PNG renders are supplementary visual evidence. The ANSI body-diff (≥2
differing bodies while the dashboard stays open) remains the authoritative
live-update gate. If `freeze` is not installed or fails, the scripts warn and
continue — the campaign is never blocked by freeze.

## Model law

All campaigns run provider `openrouter` / model `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`.
Any other model appearing in the TUI is a misconfiguration signal.

The model is named in `cfg/opencode.json` and `cfg-v1/opencode.json` and nowhere
else: `launch.sh` and `launch-v1.sh` read it out of the config, and the v2
launcher writes it into the isolated tree's `state/opencode/model.json`, which is
the TUI's new-session model preference. That pin exists because of a measurement
(2026-10-22): the v2 TUI resolves the model for a new session from the first
agent in the server's list, the built-in agents carry no model, and the TUI
therefore fell through to the first entry in the provider catalogue — "Flint
(free)" on one run and "Muse Wonder" on the next. The campaign's own session is
created by the plugin, which resolves the configured default agent and so the
configured model, and the host DB records `openrouter/nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`
for it.

The SMALL-model half is pinned the same way, by the same measurement logic: the
host resolves its small calls (session titles) by picking a small-family model
from the provider's enabled entries — a list the harness config does not control
— and a 2026-10-27 run's host log shows those calls landing on
`google/gemini-nano-banana-2.1`, a different model on the same key. Both configs
therefore set `agent.title.model` to the harness model (the config key the host
prefers ahead of its own catalogue pick), so the campaign runs one model on both
halves.

## Unattended operation

Both campaign configs deny `/dev/*` for the agent's `external_directory` reads.
Measured 2026-10-22: the campaign's agent chose to read `/dev/stdin`, the host
raised a permission prompt for it, and the prompt covered the pane for the whole
observation window — and it stalls the agent, because the agent cannot continue
until the prompt is answered. A deny needs no answer: the read is refused, the
agent continues, and nothing covers the pane. The campaign's work is inside the
workspace, so a read outside it is never legitimate here.

## Orchestrated runs, cadence, and evidence aging

- `run-all.sh` — the documented command that runs every campaign (six v1, one
  v2) against HEAD from the isolated fixture projects, under one lease per
  host type (`slot.sh`). Preflight: harness-unmodified attestation, bundle
  freshness + the 20 harness contracts, stale-evidence aging, and an
  `OPENROUTER_API_KEY` check. It relaunches each host fresh under the lease so
  boot-time events (the load briefing) are observable, runs the campaigns,
  attests the harness again afterwards, and prints state digests plus the
  transcript path. On a zero-fail run it appends a `run-all <date> commit=<sha>
  PASS=n FAIL=n SKIP=n digests=[...]` line to `runs/last-run.txt`; any failure
  leaves the evidence file untouched.
- A concurrent second invocation SKIPs (exit 0) the campaigns whose lease it
  cannot acquire — it SKIPs (exit 0) rather than failing.
- `check-evidence-age.sh` — reports whether the last recorded run matches HEAD:
  exit 0 current, 1 STALE (HEAD advanced past the recorded commit), 2 no run
  yet. This is the age tripwire: every commit after a recorded run turns it
  red until a run refreshes it. `run-all.sh` logs the same verdict in preflight.
- Cadence: run `run-all.sh` for any HEAD that carries a live-TUI claim, and
  whenever `check-evidence-age.sh` reports STALE on a HEAD whose behavior claims
  matter. There is no scheduler inside the repository (CI has no provider key);
  the tripwire is the discipline.
- `panel-excerpt.sh` — region-bound extraction of companion toast panels
  (title line + right-border column). Toast and briefing wording assertions in
  `drive-f2.sh` and `drive.sh` check the panel region, not the whole pane, so
  an agent transcript echoing a phrase cannot satisfy them. `panel_first_frame`
  extends that to a sampled frame sequence: a toast is transient, so the
  assertion about it reads every frame captured while the goal was being created
  rather than one frame taken at an arbitrary moment.
